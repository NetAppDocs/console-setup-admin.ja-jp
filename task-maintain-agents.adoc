[role="lead"]
エージェントが常に稼働状態を維持できるように、ConsoleエージェントVMにパッチを適用し、適切なサイズで正常な状態に保ってください。



[[apply-operating-system-updates-to-agent-hosts]]
== エージェントホストにオペレーティングシステムのアップデートを適用する

エージェントホストのオペレーティングシステムおよび関連パッケージにセキュリティアップデートを適用して、ホストのセキュリティを維持してください。

これはお客様の責任です。Consoleエージェントソフトウェアは自身をアップグレードできますが、オペレーティングシステムや関連パッケージをアップグレードすることはありません。


NOTE: OVAを使用してvCenterにConsoleエージェントを展開した場合、オペレーティングシステムはエージェントイメージの一部となります。link:task-upgrade-agent.html#upgrade-a-vcenter-deployed-console-agent-using-an-iso["ISOを使用してエージェントをアップグレードします"^]オペレーティングシステムをアップデートします。

オペレーティングシステムのディストリビューションについては、会社の標準手順に従ってください。OSのセキュリティパッチを適用する際に、エージェントホストサービスを停止する必要はありません。

OVAからデプロイしていないエージェントでは、サポートされている構成との互換性を維持するために、通常のOSパッチ適用中にDockerまたはPodmanがアップグレードされないようにしてください。これは、アップデート時にDockerまたはPodmanを一時的に除外するか、パッケージマネージャーを永続的に設定してDockerまたはPodmanのアップデートをスキップすることで実現できます。

以下は、さまざまなLinuxディストリビューションでDockerまたはPodmanのアップデートを除外する方法の例です。パッケージをアップデートから除外する方法に関する最新の手順については、お使いのLinuxディストリビューションのドキュメントを参照してください。

.Podmanの例
[source, bash]
----
sudo yum update --exclude=podman
sudo yum upgrade
----
.Dockerの例
[source, bash]
----
sudo apt-mark hold docker-ce docker-ce-cli containerd.io
sudo apt update
sudo apt upgrade
----


[[resize-the-vm-or-instance-type]]
== VMまたはインスタンスタイプのサイズを変更します

プロビジョニング不足のエージェントVMのCPUまたはRAMを増やして、エージェントが引き続き良好なパフォーマンスを発揮できるようにします。

ConsoleからConsoleエージェントを作成すると、デフォルト設定でクラウド プロバイダにVMインスタンスが展開されます。link:reference-agent-default-config.html["エージェントのデフォルト設定について詳しくはこちらをご覧ください"]。エージェントの作成後は、CPUやRAMの少ない、より小規模なVMインスタンスに切り替えないでください。

エージェントVMのプロビジョニングが不足しているという通知を受け取った場合は、より多くのCPUまたはRAMを備えた、より大規模なVMインスタンスへのアップグレードを検討してください。


NOTE: vCenterにエージェントをインストールした場合は、コンソールメンテナンスツールを使用してVMインスタンスのサイズを変更します。link:task-agent-vm-config.html["vCenter でエージェント VM のサイズを変更する方法"^]。

エージェントVMのCPUまたはRAMを増やす必要がある場合は、クラウド プロバイダまたはオンプレミスの仮想化プラットフォームが提供する手順に従って、VMインスタンスのサイズを変更してください。NetAppは、最適なパフォーマンスを確保するために、現在のCPUとRAMの割り当てを2倍にすることを推奨しています。以下の表は推奨されるサイジング階層を示しており、各階層は前の階層のCPUとRAMの2倍になっています。

[cols="1,1,1"]
|===
| 階層 | CPU（コア数またはvCPU数） | RAM 


| 最小 | 8 | 32 GB 


| 中 | 16 | 64 GB 


| 大規模 | 32 | 128 GB 
|===

== エージェントを監視する

エージェントVM上のディスク容量、RAM、CPUの問題に関する情報を常に把握し、それらを解決できるようにしてください。

コンソールは、ディスク容量、RAM、CPU の問題など、エージェント VM に異常がある場合に通知します。コンソール内の通知センターでこれらの通知を監視するか、電子メール通知を構成します。ディスク容量、メモリ、CPU 使用率が時々増加するのは正常ですが、頻繁に発生する場合は、解決するための手順を実行する必要があります。

たとえば、エージェント リソース (CPU、RAM、またはディスク領域) が 30 分間連続して合計容量の 90% を超えると、コンソールから通知が届きます。その後、リソース使用量がそのしきい値を下回ると、通知センターに通知が解決済み (緑) として表示されます。


NOTE: エージェントVMの変更に関してご質問がある場合は、NetAppサポートにお問い合わせください。

[[stop-and-start-the-agent-vm]]
== エージェントVMを停止して起動する

エージェントVMの停止と起動時のダウンタイムを最小限に抑えてください。管理サービスとデータサービスは、エージェントが稼働状態を維持していることに依存しているためです。

必要に応じて、クラウド プロバイダーのコンソールまたは標準のオンプレミス手順を使用して、エージェント VM を停止および起動します。

link:concept-agents.html#agents-must-be-operational-at-all-times["コンソールエージェントは常に動作している必要があることに注意してください"] 。

== Linux VMに接続する

実行中であることを確認できるように、Linux VMからConsoleエージェントのステータスを確認します。

エージェントが実行される Linux VM に接続する必要がある場合は、クラウド プロバイダーの接続オプションを使用します。

AWS:: AWS でエージェントインスタンスを作成するときは、AWS アクセスキーとシークレットキーを指定します。このキー ペアを使用してインスタンスに SSH 接続できます。  EC2 Linux インスタンスにはユーザー名「ubuntu」を使用します。  2023 年 5 月より前に作成されたエージェントの場合は、ユーザー名「ec2-user」を使用します。
+
--
https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/AccessingInstances.html["AWS ドキュメント: Linux インスタンスに接続する"^]

--
Azure:: Azure でエージェント VM を作成するときは、ユーザー名を指定し、パスワードまたは SSH 公開キーで認証することを選択します。  VM に接続するために選択した認証方法を使用します。
+
--
https://docs.microsoft.com/en-us/azure/virtual-machines/linux/mac-create-ssh-keys#ssh-into-your-vm["Azure ドキュメント: VM への SSH 接続"^]

--
Google Cloud:: Google Cloud でエージェントを作成するときに認証方法を指定することはできません。ただし、Google Cloud Console または Google Cloud CLI (gcloud) を使用して Linux VM インスタンスに接続できます。
+
--
https://cloud.google.com/compute/docs/instances/connecting-to-instance["Google Cloud ドキュメント: Linux VM への接続"^]

--
